# 赛题分析与建模设计

## 数学建模规范参考

必须读取 `../_references/modeling_integrity.md` 的“题意合同”“两条验证链”“结论—证据账本”和“多 Agent 的最小泄露协议”；如需领域判断，再读取 `../_references/math_modeling_norms.md` 中与当前题型相关的章节。不得按题号或历年常见套路选择模型。

## 必须产出

在当前工作目录的 `reports/` 子目录中创建或更新：

- `reports/PROBLEM_CONTRACT.md`：面向人的逐项题意合同、固定/可调量、歧义与验收条件。
- `reports/PROBLEM_CONTRACT.json`：与前者一致的机器可检验要求表，状态最终为 `FROZEN`。
- `reports/ANALYSIS_MODELING_REPORT.md`：
  - 赛题分析、子问题拆解、数据与附件理解、评价标准、关键歧义和假设预检。
  - 文献证据映射、候选路线比较、变量、符号、模型假设、目标函数、约束条件、求解算法、各子问题实现口径、代码阶段任务清单。

同步更新 `reports/DECISION_LOG.md`、`reports/HANDOFF.json` 和 `reports/STAGE_GATES.json`。不要在本阶段写论文正文，不要生成最终 `paper/`，不要把图表排版任务提前到这里。


## 工作流程

### Step 0: 前置门禁与允许输入

开始前必须：

1. 运行 `project_guard.py verify`，确认 `reports/PROBLEM_MANIFEST.json` 中每个白名单输入存在、哈希未变且已核验；
2. 查看 literature gate 是否被标为 `required=true`；只有被触发时才读取文献证据包、运行校验器，并要求该 gate 与人工 checkpoint 通过；未触发时不得为了“凑引用”延迟建模；
3. 确认 intake gate 为 `PASS`，以及所有已触发的上游 gate 已通过，再把 analysis gate 改为 `RUNNING`；
4. 读取 `plan.md`、`PROVENANCE.md`、`DECISION_LOG.md` 和 `HANDOFF.json`；
5. 只读取 manifest 白名单内的题面/附件和 evidence bundle 中已登记、符合任务模式的通用方法资料。`isolated-benchmark` 与 `retrospective-audit` 封存前禁止接触答案、讲评、范文、旧结果和目标数值。
6. 建立合同后、标 `FROZEN` 前，运行 `python "<本 skill>/scripts/contract_lint.py" --root .`；任何 `FAIL` 必须修复（缺失验收断言、占位符、quantities 种类错误、md/json 不一致等），不得带着错误冻结合同——合同缺陷必须在本阶段暴露，而不是留到 6verity 才发现。

任一必需前置条件缺失或状态为 `STALE/FAIL` 时停止，不得凭聊天上下文补造题面或理论。已触发的文献门禁为 `CONDITIONAL` 时，只有缺口不支配核心模型、限制已进入报告且用户明确确认才可继续，相关结论不得升级为确定事实。

### Step 1: 子问题拆解

明确编号的顶层问题只用于组织报告章节，不用于判断要求是否存在。扫描题面、附件说明和提交说明中的所有命令动词；每个计算、预测、设计、证明、比较、评价、解释、填表或提交动作都建立一个 `REQ-*`。小问不必成为独立章节，但不能从追踪矩阵消失；背景和数据说明若限定对象、范围、单位或格式，也要进入相应要求的约束。

在 `ANALYSIS_MODELING_REPORT.md` 开头明确写：

根据题目动态调整问题数量

本赛题共 X 个子问题。

每个子问题要说明：

- 输入数据和已知条件。
- 决策变量或预测对象。
- 目标函数或评价指标。
- 约束条件。
- 与其它子问题的依赖关系。
- 绘制哪些图像或表格来展示结果。

在 `PROBLEM_CONTRACT.md` 和 `PROBLEM_CONTRACT.json` 中建立追踪矩阵，至少包含：

| 字段 | 要求 |
| --- | --- |
| ReqID 与分组 | 唯一 `REQ-*`；顶层问题只是分组 |
| 原文定位 | 输入文件、页/段/工作表/单元格 |
| 动作与对象 | 精确回答“做什么、对什么做” |
| 范围与时点 | 空间、时间、样本或情景范围 |
| 固定量 | 题面给定且不得为改善结果而改变的量 |
| 决策/预测量 | 题面允许调整或要求预测的量 |
| 必交输出 | 数值、单位、精度、表格、图、文件和模板位置 |
| 采用解释 | 与歧义登记表中的决策一致 |
| 验收断言 | 可证伪、可由后续代码或审计执行 |
| 下游映射 | 代码任务、结论 ID 和论文章节，分析阶段可先留待填 |

固定量与决策变量不得重名。算法网格、容差和随机种子是控制参数，不得伪装成现实决策变量。

若合同含坐标、经纬度、距离、邻接、轨迹、覆盖、路径、方向或二维/三维几何，必须调用 `$mathmodel-spatial`。在正式定模前冻结 `reports/SPATIAL_CONTRACT.json`，明确维度、坐标系、轴顺序、单位、CRS/原点、距离度量、角度制和容差；任何 unknown 项都进入 open risks。不得从图示外观猜三维关系，也不得把离散采样可行写成连续区域可行。

### Step 2: 假设敏感性预检

列出关键歧义，不要急着定模型。对影响结果的歧义至少给出两种解释，并用简单验算或逻辑递进判断选择。

建立歧义登记表：`AMB-*`、候选解释、原文证据、影响的 `REQ-*`、影响等级、是否能由题面判定、采用/排除理由、状态和分支策略。不能从原文、附件、量纲或前后递进关系排除的重大歧义，不得由 Agent 静默选择：

- 比赛规则允许且用户能提供事实时，标 `BLOCKED` 并请求澄清；
- 用户也无法裁定时，并行求解关键解释并报告条件化结论；
- 只有有可复核证据时才能标 `resolved`；“使结果更优”“更像常见做法”不是证据。

必须在 `ANALYSIS_MODELING_REPORT.md` 中包含：

```markdown
## 假设敏感性预检

### 模糊表述及解释
...

### 快速验算与递进性检查
...

### 最终采用的解释
...

### 绘制的图像和对比表格


```

如果某个假设会让后续问题的新增条件没有边际效果，要回头调整解释.

反过来，如果某个解释只有通过增加题面未授权的自由度才产生改善，也必须拒绝。这个检查面向所有题型，不针对某一类几何或优化对象。

### Step 3: 数据理解与建模路线

对每份附件做数据理解：

- 行列规模和字段解释。
- 缺失、异常、重复、单位不一致。
- 可直接用于建模的变量。
- 需要派生的指标。

根据文献报告中至少两条候选路线做二次筛选；逐条核对结构匹配、数据要求、可识别性、关键假设、求解难度、全局/局部最优风险、验证基线、可解释性、失败模式和证据强度。说明选中路线与放弃路线的可证伪理由，不能因算法熟悉、容易编码或单次结果较好直接定模。

然后给出总体路线：

```text
题面 -> 数据清洗(EDA) -> 子问题一模型 -> 子问题二模型 -> 。。。。 -> 结果检验 -> 论文展示
```

先建立最简单的可检验基线，再根据误差结构、机理、约束和数据量选择更复杂模型。禁止因为比赛名称、题号、历史获奖频率或模板内置示例直接指定算法。每个复杂模型都要写出相对基线的必要性和失败条件。

### 候选路线 → 机器可读候选池（交给 3coding 对比实验）

对含优化、搜索、预测或参数估计的子问题，在选定主路线后，用 `$mathmodel-algorithm-lab` 的 selector 按问题结构生成候选池，供 3coding 阶段执行统一预算的对比实验：

```bash
python "<mathmodel-algorithm-lab skill>/scripts/algorithm_selector.py" \
  --registry "<mathmodel-algorithm-lab skill>/assets/algorithm_registry.json" \
  --variable <continuous|discrete|mixed> --objective <single|multi> \
  --constraints <none|linear|nonlinear> --differentiable <yes|no|unknown> \
  --convex <yes|no|unknown> --evaluation-cost <low|medium|high> \
  --domain "<本题领域>" \
  --output reports/ALGORITHM_CANDIDATES_<子问题>.json
```

- 每个这类子问题产出一个候选文件；只有单个优化型子问题时可直接命名 `reports/ALGORITHM_CANDIDATES.json`（6verity 会核对该文件）；
- 输出中的 `research_queries` 交给文献检索阶段核验原文与适用条件；核验后把各候选的 `selection_status` 更新为 `SELECTED`/`REJECTED` 并附理由；
- 候选池必须含确定性基线 + 主算法 + 结构不同的替代算法；能用精确法时不因某算法"流行"而跳过；
- 无法结构化（纯解析推导）的子问题记 N/A，不要为凑文件而生成候选。

若任务由观测反推物理参数、隐状态、源项或系统结构，按逆问题处理。建模报告必须区分目标参数、干扰参数和算法控制量，说明前向模型、参数可识别性与可能的等价解；至少保留一个结构不同的简单反演基线。材料常数、标定量或边界条件只有在题面或已核验证据支持时才能固定；否则纳入联合估计、区间/场景分析或系统误差传播，不能用一个方便常数替代后再只报告重复性误差。

### Step 4: 建模报告

在 `ANALYSIS_MODELING_REPORT.md` 中写出可交给代码阶段实现的完整方案。

每个子问题至少包含：

- 问题目标。
- 符号和变量。
- 模型假设。
- 目标函数。
- 约束条件。
- 求解方法。
- 输入输出。
- 代码实现要点。
- 结果校验方法。
- 文献证据映射：每个外部公式、定理、算法、指标或参数对应的 `source_id`、`claim_id` 和原文定位。
- 证据属性：明确区分文献结论、本题可检验假设、工程近似和本项目推导。
- 替代路线、否决条件及需要由代码检验的失效模式。

公式要清楚到代码阶段能直接实现。算法描述要包含核心步骤、停止条件、复杂度或可行性说明。验证计划必须分开写“语义验收”和“数值验收”，并为每个 `REQ-*` 指定至少一个可证伪测试；不能只计划用同一程序导出的另一份文件做一致性检查。

推荐结构：

```markdown
# 建模报告

## 1. 总体建模框架
## 2. 数据处理方案
## 3. 符号说明
## 4. 文献证据映射与候选路线比较
## 5. 问题一模型
## 6. 问题二模型
## 7. 问题三模型
    .... 
## 8. 灵敏度、全局性与基线检验方案
## 9. 代码实现任务清单
```

如果子问题数量不是 3 个，按实际题面调整章节，不要硬凑。

### Step 5: 给代码阶段的接口

在 `ANALYSIS_MODELING_REPORT.md` 末尾写一个“代码实现任务清单”，格式如下：

```markdown
## 代码实现任务清单

| 任务 | ReqID | 输入 | 固定量 | 决策/预测量 | 输出 | 方法 | 文献证据/本题假设 | 独立校验 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 问题一 | ... | ... | ... | ... | ... | ... | source_id / 本题假设 | ... |
| 问题二 | ... | ... | ... | ... | ... | ... | source_id / 本题假设 | ... |
```

### Step 6: 独立题意审查与合同冻结

在有多 Agent 能力时，启动一个最小上下文审查者：只给原始白名单题面和附件，不给主解合同、拟采用模型、代码、结果或目标数值。让其独立抽取原子要求、固定量、可调量和重大歧义，并按“发现—原文位置—严重级别—建议测试”返回。没有多 Agent 时，清空主解结论后从原题逐条反向审查。

合并审查差异，但不能用多数票替代原文证据。满足以下条件后才能把 `PROBLEM_CONTRACT.json` 标为 `FROZEN`：

- 所有白名单材料均已读取和核验；
- 文献 evidence bundle 已通过，所选模型/算法/指标均能回到已核验来源或明确的本题假设；
- 每个命令式要求、输出模板和指定时点都有 `REQ-*`；
- 固定量与决策/预测量分离；
- 无未处理占位符和重大未决歧义；
- 每个要求都有验收断言和下游任务；
- `contract_lint.py` 无 FAIL；每个优化型 REQ 有候选池文件（或明确的 N/A 理由）；
- JSON 中记录 `PROBLEM_MANIFEST.json` 的当前 SHA-256，并与 `PROBLEM_CONTRACT.md` 一致。

JSON 还必须提供顶层 `quantities`，为每个量记录唯一 ID、`kind=fixed|decision|state|control|derived`、单位、定义/值或定义域及来源 ReqID；后续 claim 使用这些 ID 声明实际使用的量。以 `python <6verity skill>/scripts/integrity_check.py --print-schema` 为机器 schema 的权威说明，不自行发明同义字段。

为每个存在实质分歧的 ReqID 分别快照题意/模型候选；共享模型使用独立 task ID。先让人类查看候选差异、证据和影响，再引用 contract 与 model 人工审查事件 `select`。冻结后若合同改变，在 `DECISION_LOG.md` 追加“触发证据、旧/新决策、影响 ReqID、作废产物、需重跑阶段”，把依赖 gate 标为 `STALE`。不得静默覆盖旧解释。更新 `CURRENT_VERSIONS.json` 和 `HANDOFF.json`；分析 gate 只有在合同冻结、独立审查完成、contract/model 人工签认且无重大未决项时才可 `PASS`。模拟豁免只能得到 `UNVERIFIED`。


## 质量要求

- 所有结论都能回到题面、数据、已核验文献证据或明确标注且可检验的本题假设。
- 不编造数据字段和数值。
- 不编造引用、DOI、原文结论或证据定位，不采用未登记的新来源。
- 不跳过歧义分析。
- 不以内部数值一致代替回答原题，也不开放题面未授权的自由度。
- 模型既要有数学表达，也要能被代码实现。
- 非凸优化或启发式求解必须设计多起点、松弛界/理论界、替代求解器、穷举子域或强基线中的至少一种可执行全局性检查；没有证明时只能声称 `best_found`，不得把单次局部最优写成全局最优。
- 若数据不足或题面不清，要明确记录风险和替代方案。
- 通用流程中不得写入当前赛题答案或按题号触发的方法；题型特定检查必须声明适用条件。
